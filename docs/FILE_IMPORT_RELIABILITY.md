# 文件导入、去重与失败恢复

本文描述 2026-10-17 已上线的文件导入行为。格式入口及小助手 Excel、离愁轩 Wiki 的资料边界见 [第三方历史记录迁入](RESCUE_FILE_IMPORT.md)。官方凭据抓取走独立后端，不能套用本文的分批文件保存合同。

## 使用与恢复

1. 在桌面或手机的导入入口选择「文件」，上传原始导出文件。
2. 核对识别条数、卡池、游戏 UID 和区服；按预览要求完成账号验证或填写账号。B 服与官服分别保留，不能只凭相同 UID 合并。
3. 确认后保持页面打开，等待服务器核对已有记录、保存待新增记录，再刷新总览。识别出文件内容不等于云端已保存。
4. 若提示部分完成，保留预览并再次确认导入。客户端重新读取服务器已有记录，只继续保存缺少的部分；无需先删除数据。
5. 若预览已关闭或过期，重新选择原文件并核对账号后导入。不要通过轮流上传同一份资料的不同格式来判断保存是否完成。

例如文件含 2164 条明细，第一次保存到 400 条后中断，重试核对到这 400 条后，待保存量为 1764 条。进度中的分母是本次待保存量，成功保存数与服务器跳过的重复数共同构成这一批的确认回执。

文件预览在当前标签页的 `sessionStorage` 中保留，默认有效期 30 分钟；它不承担后台持续上传。刷新后恢复的是待确认资料，需要重新核对账号并确认，不自动恢复进行中的请求。这里与工作台手动草稿的 24 小时合同不同，关闭标签页、清理网站数据或存储不可用时不能依赖草稿恢复，请保留原文件。

## 三种数量如何核对

- **预览识别条数**：本次文件展开后的明细数量，尚未扣除服务器已有记录。
- **服务器确认条数**：每批保存响应中的 `saved.history + skipped.history`。遇到错误或回执数量不符时停止，并保留预览。
- **账号和总览读数**：账号清单、当前账号／区服的分析快照及所选卡池筛选各有范围；赠送等非寻访获取、补录已知量和未知量也有各自统计规则。文件明细数量不能直接当作每个图表的抽数分母。

总览更新由个人分析快照完成，保存后暂时显示旧快照或构建状态时，按页面提示刷新或等待更新。核对当前 UID、区服、卡池和筛选，再比较相同范围；规则见 [账号分析范围](ACCOUNT_ALL_CLOSEOUT.md)、[统计指标](STATS_OBSERVATION_CONTRACT.md)和[个人分析 Worker](PERSONAL_ANALYSIS_WORKER.md)。

## endgacha.kwer.top 格式合同

- 校验 JSON：识别 `info.export_app=endgacha`、`info.export_type=gacha`、非空 `info.verify` 及批次 `data`，读取 UID、渠道、卡池 ID、批次末序号、小数秒时间和可用的免费标记。`official` 映射官服 `1`，`bilibili` 映射 B 服 `bilibili`。格式名称表示来源带有校验字段；当前适配器不验证来源签名的密码学有效性。
- 纯寻访 JSON：读取批次映射，保留存在的卡池 ID 和序号；文件本身没有账号信息，需在预览中确定所属账号。
- 纯寻访 TXT：按时间、卡池名及 `名称-原始星级-是否首次获得[-是否免费]` 展开。第四段可省略；来源未提供免费标记时保留“未提供”的信息，匹配时不把它当作明确的付费证据。本站新导出的 TXT 写出第四段，保留已有免费标记。
- 来源原始星级 3／4／5 映射本站 4／5／6 星；小数秒时间按秒转换，保留毫秒。批次末序号存在时，按批次长度还原各条的原始序号；缺少时仅生成导入标识，不能当作官方序号证据。
- TXT 缺少卡池 ID 时按当前目录的唯一同名卡池匹配；同名歧义阻止导入。没有目录匹配的名称沿用已有来源占位 ID 规则，不猜测官方身份。

## 去重范围与数量保护

保存前通过鉴权的 `GET /api/account-gacha-data` 读取当前网站用户完整明细。必须确认 `meta.ownerId` 是当前用户，且 `meta.truncated` 不为真；读取失败或截断时保留预览，不凭本机部分历史推断云端状态。

合并先保留真实序号匹配，再处理缺少原始序号的 kwer 合成记录。内容匹配要求相同游戏 UID、区服、卡池、毫秒时间、名称和星级；明确提供的免费属性不能冲突。kwer 没有表达的特殊获取类型不覆盖已有记录，已有官方明细或站内 JSON 明细也可参与匹配。两条均有不同真实序号时，不能仅因名称和时间相同就合并。

每条已有记录最多匹配一次。同批十连中的九把相同武器仍是九条；批次顺序相反、只保存半批、一个条目省略免费属性而另一个明确提供时，均按实际数量逐条消耗，不以集合去掉同名物品。明确属性优先于缺失属性匹配，返回的新增记录保留文件顺序。

旧 TXT 占位卡池在当前目录有唯一同名目标时可用于判重；这一匹配不会改写已存卡池 ID、免费状态或特殊获取类型。不同区服、未知归属、同名歧义或时间精度不同的历史不自动归并，需另行核对。此次修复不会自动清理旧版已经写入的重复数据。

## 保存与失败边界

`useDataExportImport` 依次执行：开放时间及账号检查、读取服务端历史、计算新增量、保存缺少的卡池、每 100 条保存明细、保存补录、应用本地数据并请求个人快照刷新。

- 卡池保存返回失败，或明细回执不等于当前批量，都会停止后续保存并保留预览。
- 同一导入不能重复并发提交；进度更新保留已完成的账号确认。保存期间关闭入口禁用，失败后可以继续确认或关闭。
- 全部写入完成前，不把整份文件加入本地历史来表示已保存。失败重试重新核对服务端，不以本机曾显示的预览作判断。
- 明细的多批写入与补录提交不是一个整体数据库事务。前面成功的批次可能保留；补录继续使用工作台自己的校验令牌、修订及原子提交合同。
- 保存后的总览刷新失败也会保留预览；重试先核对已存记录，避免再增加一份。成功回执不承诺后台快照已经计算完毕。

## 手机弹窗与删除入口

工作台文件确认弹窗通过 `createPortal(..., document.body)` 脱离卡池工具栏的层叠上下文，避免被底部导航覆盖。手机设置弹窗使用 `100dvh`、安全区边距、受限高度和纵向滚动，层级高于通知入口；在短屏和横屏可滚动到操作区。

设置中的「删除我的数据」使用本机明细与个人账号快照 `recordCount` 判断是否存在数据，不能因本机只加载部分明细或尚未加载明细而误禁用。它与「注销账号」是不同操作，删除范围由已有接口决定，不会因为这次按钮修复而扩大。

处理旧重复记录前先导出备份并确认范围。若只有这一份原始明细需要保留，可在了解「删除我的数据」的全部范围后自行清空并重新单次导入；有其他账号、补录或人工修改时，应在工作台核对，不能直接覆盖整份历史。
