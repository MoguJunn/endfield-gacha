# 官方限定池信物导入修正

2026-09-30：限定池达到 240 抽后的信物事件可能只包含“角色名的信物”、
官方序号和时间，没有物品 ID 或品质。旧逻辑把它作为未知四星寻访写入，
使非免费抽数增加 1、四星数量增加 1、后续保底多推进 1，且时间线没有赠送节点。

修正使用目录中限定池的 UP 名称做精确匹配，识别条件为：限定池、名称等于
`UP名称 + 的信物`、官方未提供 ID 和品质。不会按缺少 ID/品质直接猜测赠送，
不放宽官方序号、时间与账号作用域校验。导入补齐目录中的 UP 配置；将信物保留为
`special_type=gift`，角色名使用 UP 名称，物品名保留原“角色名的信物”。品质 6
用于已有赠送展示合同，不把它当作一次六星寻访。原始暂存摘要保留缺少 ID/品质的事实。

已有统计合同会排除赠送记录的抽数、普通掉落数量、保底和胜率，时间线显示赠送节点。
重复导入仍由账号、区服、卡池与官方序号去重。没有新增前端兼容分支或分析 schema 版本。

## 维护与回退

实际执行前重新核对候选数量；选择不存在且不含空格的私有备份路径，避免覆盖。
使用 `psql -X -v ON_ERROR_STOP=1`，设置 `expected_token_count`、`backup_file`；
不设置 `apply_repair` 时默认 ROLLBACK。只有已授权的维护操作才设置
`apply_repair=true`。单次修复不修改分析函数或调度；既有历史 revision 触发器负责重建。

备份是 PostgreSQL COPY 文本格式的一行 JSONB。回退时在同一事务创建临时表
`repair_backup(payload jsonb)`，使用 psql 的 `\copy repair_backup FROM '私有备份路径'`
读取。展开 `history` 数组，按用户、游戏账号、区服、卡池、官方序号定位，先核对
当前修改字段与备份 `new_row` 一致；若用户随后编辑或再次导入，停止自动恢复。
核对后恢复 `old_row` 中的品质、赠送类型、角色名、保底和标准标记，增加编辑版本，
再按异常提醒主键恢复其原状态。提交后让 revision 队列重新生成快照，不直接覆盖
缓存 JSON。后端回退使用保存的旧源码和镜像，只替换对应服务。
