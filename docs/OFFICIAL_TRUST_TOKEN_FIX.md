# 官方限定池信物导入修正

此修正随 PR #42 发布（2026-09-30）。本文说明识别合同、存量修复和回退方法。

限定池达到 240 抽后的信物事件可能只包含“角色名的信物”、
官方序号和时间，没有物品 ID 或品质。旧逻辑把它作为未知四星寻访写入，
使非免费抽数增加 1、四星数量增加 1、后续保底多推进 1，且时间线没有赠送节点。

修正使用目录中限定池的 UP 名称做精确匹配，识别条件为：限定池、名称等于
`UP名称 + 的信物`、官方未提供 ID 和品质。不会按缺少 ID/品质直接猜测赠送，
不放宽官方序号、时间与账号作用域校验。导入补齐目录中的 UP 配置；将信物保留为
`special_type=gift`，角色名使用 UP 名称，物品名保留原“角色名的信物”。品质 6
用于已有赠送展示合同，不把它当作一次六星寻访。原始暂存摘要保留缺少 ID/品质的事实。

已有统计合同会排除赠送记录的抽数、普通掉落数量、保底和胜率，时间线显示赠送节点。
重复导入仍由账号、区服、卡池与官方序号去重。没有新增前端兼容分支或分析 schema 版本。

## 验证

- `api/__tests__/officialTrustTokenGift.test.js` 覆盖完整后端导入到个人分析：
  291 次普通寻访 + 10 次免费寻访 + 1 个信物事件，统计分别为 291/301，
  赠送节点为 1；信物不推进/重置保底，重复导入不会增加记录。
- 回归范围包括精确匹配与负例、原有导入/暂存、重构池、个人快照、时间线、资源与模拟器。
- `node scripts/verify-official-trust-token-repair.mjs` 使用无宿主端口的临时 PostgreSQL
  容器验证存量脚本：默认演练回滚、备份可读取、实际更新、跨池保底、免费六星、
  不同账号相同旧 record_id 的隔离、异常提醒收口及重复执行。默认使用 PostgreSQL 17，
  不连接生产数据库。

## 部署与存量修复要求

- 私有导入后端需要同步更新 `fullImportService.js` 与共享规范化模块；更新前确认
  导入队列已处理完毕，并保留可回退的源码与镜像。
- 存量脚本 `supabase/manual/repair_official_trust_token_gifts.sql` 默认只演练，
  不进入自动迁移或新环境 baseline。候选必须匹配目录 UP、提交完成的原始暂存记录、
  原名称/品质/ID/时间/官方序号，并排除人工编辑。更新使用完整复合作用域，
  不能只按旧 record_id 定位。锁内再次核对候选，数量变化即停止。
- 修复前写入精确旧/新行与异常提醒备份，保存在受限运维位置，权限 600。
  使用 psql 输出备份，不增加数据库文件访问权限；作用域或权限检查失败即回滚。
- 修复不新增或删除历史记录。提交后检查受影响 owner/scope、个人统计、单池和旧公共
  统计是否已按新 revision 发布，以及是否存在失败任务；历史验收结果不能代表当前队列状态。
  刷新遵循既有调度周期，不为验证结果提前修改调度时间。

## 维护与回退

实际执行前重新核对候选数量；选择不存在且不含空格的私有备份路径，避免覆盖。
使用 `psql -X -v ON_ERROR_STOP=1`，设置 `expected_token_count`、`backup_file`；
不设置 `apply_repair` 时默认 ROLLBACK。只有已授权的维护操作才设置
`apply_repair=true`。单次修复不修改分析函数或调度；既有历史 revision 触发器负责重建。

备份是 PostgreSQL COPY 文本格式的一行 JSONB。回退时在同一事务创建临时表
`repair_backup(payload jsonb)`，使用 psql 的 `\copy repair_backup FROM '私有备份路径'`
读取。展开 `history` 数组，按用户、游戏账号、区服、卡池、官方序号定位，先核对
当前修改字段与备份 `new_row` 一致；若用户随后编辑或再次导入，停止自动恢复。
核对后恢复 `old_row` 中的品质、赠送类型、角色名、保底和标准标记，增加编辑版本，
再按异常提醒主键恢复其原状态。提交后让 revision 队列重新生成快照，不直接覆盖
缓存 JSON。后端回退使用保存的旧源码和镜像，只替换对应服务。
